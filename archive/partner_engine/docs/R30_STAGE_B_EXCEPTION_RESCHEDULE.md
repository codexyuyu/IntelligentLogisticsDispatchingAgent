# R30 阶段 B：异常事件与动态重调度交付说明

**基线**：完全继承 R30-A 单现役仓库 `WH001` 和 R28 原计划对账；历史 `WH002` 引用及以前的数据库/实验/工程文件不删除。**工作模式**：重新读取当前合成/业务快照 → 重新验证 R30-A 基线 → 依异常时刻冻结历史 → 对仍在仓库的剩余任务重新运行 CP-SAT / OR-Tools → 独立检查后缀交付与来源 → 生成只读的对比和 3D 时间轴投影。没有写库操作，不改变真实订单履约、库存、派车指令或历史计划。

## Windows 使用方法（不需要再次导入 R30-A 数据）

1. 解压整个 `R30_STAGE_B_DYNAMIC_EXCEPTION_RESCHEDULE.zip` 到一个**新目录**。保留原有 R30-A 工程和数据库备份，不覆盖老工程。所有命令使用本机 Python/Node，按本机已配置 PostgreSQL 17 服务运行。若虚拟环境或依赖未安装，在 `backend` 目录执行 `python -m pip install -r requirements.txt`；需要 Windows 可用的 OR-Tools 与 PostgreSQL 连接驱动。建议 Python 3.11/3.12。
2. 在 PowerShell 进入新包 `backend` 目录：`powershell -ExecutionPolicy Bypass -File .\start_pg_r30b_local.ps1`。交互输入数据库密码（密码不写入文件）。脚本设置 `PG_PREVIEW_WRITE_ENABLED=0`，仅绑定 `127.0.0.1:8000`，不创建任何表、不重复迁移、不自动导入 CSV。数据库本身应已按 R29 和 R30-A 完成相应安全迁移/业务资料导入；若缺少这些表，真实 PG 模式将如实失败，但内置纯合成模式仍可运行。
3. 另开 PowerShell，在 `frontend` 目录依次运行 `npm ci`、`npm run build`、`npm run dev`；浏览器进入 http://127.0.0.1:5173，左侧进入「智能调度 → 单仓仓运闭环」/“R27 仓运闭环”（菜单以实际版本为准）。**前端若使用打包内的旧 Windows 依赖，仍应执行 `npm ci` 以保证可复现的锁文件依赖。**
4. 先运行正常的 R27/R30-A 单仓联合求解，检查 20 单（或 PG 实库同温区选定单）、CP-SAT 作业、OR-Tools 车辆路线、原 R28 订单级 `passed`。在新「R30 阶段 B」区域选择车辆/仓储资源/批次、设置相对仿真起点的秒数，点击「模拟异常并重新调度」。查看时间前缀与后缀、未服务原因、车辆所在路段、原/新车辆和送达时刻；切换原方案与异常预览及两种 3D 视角，导出一份包含全部原始方案和后缀证据的 JSON。
5. 仅使用 `verified_postgres` 才是 PG 数据驱动；若 R30-A 来源为 `explicit_synthetic_demo`，这仍然是数据库**保存的合成演示**，不能宣传为采集的真实物流订单。旧四车演示模式和单仓 3D 叉车动画均为可视化映射，不是 GPS、IoT 或真实叉车控制。

## 四类异常和可达边界

| 异常 | 真正改变的算法输入与处理 | 防止错误行为 |
| --- | --- | --- |
| 车辆途中故障 | 按 t 判定已送达、已发车、仍在仓库车辆，故障车辆不可用；剩余未发车车辆才可进入 OR-Tools | 车上货物不在仓库，除非具备明确可验证转运地点/时间（当前工程尚无此子模型），否则标记 `stranded_...` 待人工转运，不能凭空重配送 |
| 配送行驶延误 | 按调度时刻增加前方未达停靠点的时间，重新检查客户时间窗、保鲜期与车辆班次；未发车车辆可改变最早可用时间 | 已完成停靠、已在途车辆位置均冻结；窗口不满足则未服务/待处置，不能假装按时送达 |
| 仓储资源/月台停用 | 指定仓储资源从事件时刻不可用，冻结已开始作业，CP-SAT 仅排后续仍合法作业，时间更新再传给运输 | R27 已登记资源不可擅自换成未核验设备；停机时正在处理的作业视为中断，不记未来自动完成 |
| 库存批次隔离 | 隔离后剩余相关订单不得出库；在途相关车辆和未配送货物触发质量暂停；未完成相关仓储作业中断 | 不自动增补库存、变更批次、召回已交付订单或改变实际库存；无真实合法替换分配则显式无法服务 |

R30-A 的 R24 库存记录原始字段为`数量/温区/有效期`，**不包含可核实的最新预占锁定、实时质检或隔离剩余量**。阶段 B 已将这些批次记录映射到 Snapshot 以用于显式异常模拟，但不得将其当成实时库存台账。当前仅识别现有订单绑定批次；跨批次补货/重新分配需未来另建经过验证的操作，不会悄悄进行。

**安全核验规则**：独立 R28 验证原完整计划；异常后已发生事件及交付固定不变；禁止车辆瞬移、订单重复送达；后缀运输调用 `validate_transport`，CP-SAT 由原仓储独立校验器验证；校验总订单 `已完成+预测送达+未服务 = 全部订单`。若后缀求解无解，允许 `unserved`，不能将不可行情况假装成成功。回放合成 `replay.plan.validation.status='not_checked'` —— 混合时间轴不可直接当可执行的全历史 CandidatePlan；独立的 R30-B `verification.status='passed'` 只说明相关约束/对账通过，不证明真实货运已发生。

## Windows 人工验收清单（重要）

- [ ] 先确认 R30-A 原样跑通：单仓 WH001、20 条记录（或实际温区范围）、仓储 40 项、四辆车、R28 对账结果通过；R29 的 WH002 历史 4 条路线未被删除/改写。
- [ ] 车辆故障：在至少一单交付、但故障车未回仓的时刻设置异常；校验已交付不重复、车载订单待人工转运、3D 故障车原地冻结。
- [ ] 延误：同一在途车辆分别设置可行短延误和不可行长延误，检查预报时间变化及超窗原因；不以演示线路充当 OSRM 真实道路。
- [ ] 仓储故障：选择作业尚未完成的指定资源；已完成作业和原历史时间前缀不变，后续不得再使用停用资源，相关订单按能力真实重排或未服务。
- [ ] 库存批次隔离：使用现有批次，确认无跨批次虚构替换、无自动库存写减；在途命中批次的车辆会暂停等待人工质量处理。
- [ ] 切换「原方案 / 重排预览」，在时间轴拖动至异常前、发生时、异常后与终点；确认仓库/车辆映射及全程计划/当前已回放/未服务三种数字相容。
- [ ] 输出完整 JSON、保存后端运行日志；关闭服务后复查正式 PG 业务表、旧方案行数和 WH002 外键锚点**均未更改**。

## 当前已做的自动化检查与已知限制

- Python 快照/事务边界/各异常路径及已有 R23–R30A 定向回归已在当前隔离环境执行（结果见开发日志）。TypeScript 类型检查通过；但环境无 OR-Tools / Postgres 实库，故**没有**完成新代码的真实 CP-SAT/OR-Tools 异常后缀求解，更不能声称已通过你的 Windows 实测。
- 本环境的前端依赖是原包自带 Windows 版 `node_modules`，缺少 Linux 版 `rollup` 原生组件；`tsc --noEmit` 可执行，但 Linux 下完整 Vite build 失败。这不等于 Windows 构建成功；Windows 需执行 `npm ci && npm run build`。
- 当前未实现可在途转运、实际温湿度采集、在途多趟车辆复用、跨批次自动质量合规替换、实际道路 OSRM（用户暂不配置）、实库修改和用户授权确认执行，也未完成 AI Agent 端到端集成。这些工作**不应用模拟成功状态掩盖**。
