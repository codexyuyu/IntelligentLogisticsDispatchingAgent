| 2 | A 仓储求解与本域 API；B 运输求解与本域 API；C 作业提交/查询与校验入口；Codex 做表单和结果表 | 单模块约束反例能拒绝；记录本机速度，调整预算和规模 |
| 3 | C 实现有界仓运联动；A 确认预留；B 时间链与运输校验；Codex 展示路线与仓储时间轴 | 结构化输入→完整计划→联合校验→确认闭环；能发现“各自可行但联合冲突” |

| 9 | 功能冻结，A 安装与仓储章节；B 场景包与运输章节；C 证据索引与协调章节；全员录制，Codex 收尾前端 | 所有 R01-R10 有对应证据；换一台/干净环境能运行；版本与许可证记录完整 |
| 10 | 只做集中 bug 测试、修复与回归，全员互换操作角色 | P0/P1 清零、修复后回归、演示反复重置可成功、最终视频与代码版本一致 |

第 10 周不新增平台、复杂温舱、算法或图表大改。平时测试不会推迟到第 10 周；最后一周用于全面发现集成和边界缺陷。

## 可行性门槛与收缩

- 第 2 周若本机环境或求解轮转不稳定：固定 20 单与预计算矩阵，先打通纯结构化闭环，延后在线路网。
- 第 3 周若联合方案不稳定：保留两个仓和真实仓运衔接，缩小资源类型/规模；禁止通过独立展示两张可行表冒充协同。
- 第 5 周若多节点转运过重：保留多仓配送与入库接收仓选择，跨仓转运仅做一条预定义交接链；文档明确支持范围。
- 第 7 周若语言理解质量低：保留结构化确认和有限意图，大模型仍有可演示的工具调用/解释价值；不绕过关键确认。
- 第 8 周若速度不达目标：锁定能通过的场景规模，报告压力测试结果，优先缓存与有界重排；不宣称“全场景秒级”。

## 竞赛与创新训练交付包

| 材料 | 必须包含的证据 |
| --- | --- |
| 作品简介与团队介绍 | 冷链协同问题、范围、三人实际贡献、与开源的关系 |
| 技术方案 | 领域对象、模块边界、仓运联动、幻觉控制、实验设置和限制 |
| 系统原型与源码 | 固定版本、安装说明、样例数据、演示重置、核心功能 |
| 5-8 分钟演示视频（建议时长） | 需求到调度、异常到修复、不可行/不确定案例、实验对照 |
| 模型与工具调用记录 | 脱敏提示、输入输出、来源、延迟、失败、工具轨迹 |
| 场景与实验包 | 来源、合成参数、种子、矩阵、版本、基线、原始数据、图表 |
| 创新训练过程材料 | 周报、分工、实验记录、阶段总结；按本校通知补中期/结题表 |
| 第三方清单 | 直接依赖和借用片段、固定版本、许可证、修改说明 |

创新点应落在可量化的三项：仓运有界协同是否减少冲突，冻结执行状态的局部重排是否降低时延与扰动，约束来源与独立校验是否减少错误执行。调用现有求解器本身不是自研算法；四角色名称和聊天界面也不是实验贡献。

建议演示顺序：导入两仓场景 → 输入自然语言并确认约束 → 观察路线与入出库联动 → 注入冷间故障并改选仓/重排 → 输入无兼容车辆订单看拒绝 → 展示基线、耗时和原始证据。视频时长仅为设计建议，最终以赛制规定为准。

尚需在第 1 周补全：实际报名比赛/赛道、最终截止时间、评分表、提交格式、导师认可的冷链规则和可用设备。现在的路线覆盖已见申请书与公开命题，不能替代最终比赛通知。
