# 四周完整最小 Demo 时间规划

制定日期：2026-09-09。当前分工：你负责 A（仓储）＋C（协调与可信执行），并监督 B；B 负责运输与仿真基础；前端由 Codex 完整承担。第三位成员未明确的新职责不计入可交付人力。

本表替代原九周计划的前四周安排；第 5–9 周继续扩展与实验，第 10 周仍保留最终集中回归。四周目标是一个完整可运行的最小闭环，不代表申请书所有能力或最终竞赛要求已完成。

## 时间与人力假设

- 以今天为第 1 天：第 1 周 9/9–9/15，第 2 周 9/16–9/22，第 3 周 9/23–9/29，第 4 周 9/30–10/6。实际启动日变动时整体顺延。
- 你每周约 24 小时：仓储 8 小时、协调/集成 9 小时、检查 B 与接口协商 3 小时、测试/文档 4 小时。学习包含在各模块时间内，不能另占一整周只读源码。
- B 每周约 18 小时：运输/仿真实现 10 小时、学习与对接 3 小时、测试/文档/缺陷修复 5 小时。
- 每周 6 个工作日，另 1 天作为休息或机动；表中的 D1–D6 是本周工作日。你的平均工作日投入约 4 小时，B 约 3 小时。
- Codex 的工作由你按里程碑发起并验收；本规划本身不会自动在未来启动开发。前端之外可让 Codex 协助样板代码、测试和部署脚本，你仍负责领域规则与最终判断。
- 若你每周只能投入 10–12 小时，不能沿用同一范围和日期：应先缩小场景、让 Codex 承担更多工程实现，或延长周期。具体学习基础和机器环境尚未实测为该人力估计背书。

## 第四周必须能演示的闭环

打开工作台 → 导入内置订单 → 输入一条限定范围的调度指令并确认抽取字段 → 求解仓储与运输 → 展示路线、装卸时间和校验报告 → 确认计划 → 注入一次延误或月台故障 → 保留已发生事实、重排未执行任务 → 查看新旧差异与处置记录。

| 范围 | 四周内实现 | 明确的简化 |
| --- | --- | --- |
| 场景 | 2 仓、4 辆单温区车、20 个配送订单、冷藏/冷冻两类、1 天窗口 | 合成数据；订单所属仓和库存位置固定，不做自动换仓、跨仓中转 |
| 仓储 | 每仓装卸/月台和分拣资源；任务先后、资源互斥、已有占用；库存/预留数量 | 固定资源能力；暂不做时变温舱、清洁模式切换、7 天预约 |
| 运输 | 重量/体积容量、温区匹配、服务开始时间窗、服务时长、返回仓库 | 固定且有来源标记的矩阵；一车一趟；不接实时地图/天气 |
| 协同 | 仓库就绪时间约束车辆出发；车辆到仓时间约束卸货占用；最多 3 轮反馈 | 明确初始库存或卸货任务支撑装货；不能展示两张互不关联的结果表 |
| 异常 | 出发延误、月台不可用两类事件；重排剩余任务，记录前后变化 | 事件在作业边界注入，维修时长作为场景已知输入；不做运行中抢占/恢复，也不声称已实现最小局部影响集 |
| 可信性 | 字段来源、实体核对、必需信息缺失时澄清、独立联合校验、确认时版本检查 | 大模型仅支持“请求规划现有订单”“解释当前计划”等有限意图；不能自由改库存、温区和硬约束 |
| 运行 | FastAPI＋PostgreSQL＋React，一个后端应用；作业受限执行；状态/计划/事件可保存和重置 | 单用户演示；最小作业领取/失败恢复；不做多租户、高可用或分布式平台 |

自然语言入口需要一条真实、脱敏的模型调用记录。没有模型服务时仍能用结构化表单完整调度，但交付应标注“模型入口未验收”，不能把假返回包装成真实智能体。API 密钥仅在后端环境配置，不放页面和仓库。

## 监督 B：每周只设三次固定检查

| 时间 | 时长 | 你让 B 当场做什么 | 判断标准 |
| --- | --- | --- | --- |
| D1 | 20 分钟 | 确认本周最多 3 个交付项、输入/输出和阻塞点 | 能用具体场景描述完成条件，不能只说“研究算法” |
| D3 | 20 分钟 | 跑一个正常例和一个反例，说明剩余困难 | 能看到真实输出和测试；字段/接口问题当天解决 |
| D6 | 40 分钟 | 在你的机器按文档跑，再接入主项目验收 | 可复现、可合并、结果可解释；不以录屏代替可运行交付 |

每次交付固定包含四样：代码提交、可复现输入、验证结果、当前限制。每天只更新一句“完成什么、卡在哪里、下一步是什么”；出现超过半个工作日的阻塞立即提出，不等周会。

你不需要逐行盯 B。重点问四个问题：这个容量如何累计？时间窗约束开始还是结束？未找到解能否区分原因？重排有没有改掉已完成事实？你同时维护一组跨模块反例来抽查。

| B 的周验收门槛 | 必需证据 |
| --- | --- |
| W1 | 普通配送、超载、温区无兼容车、不可达时间窗；输入有变化时输出会变化 |
| W2 | 仓库装货延后导致运输时间变化；返回完整时间链；没有遗漏必服务订单 |
| W3 | 延误后只规划未执行运输；同输入/种子可重放；事件 ID 不重复生效 |
| W4 | 干净环境运行、可重复测试记录、无阻断缺陷、清晰失败原因与限制 |

## 第四周验收矩阵

| 检查 | 通过条件 |
| --- | --- |
| 正常闭环 | 2 仓/4 车/20 单得到计划，所有必服务单有去向，完整独立校验通过 |
| 真实协同 | 移动装货就绪时间能影响出发和服务时间；回仓卸货占用也受实际到达约束 |
| 不可行输入 | 超载、温区不匹配、不可达时间窗均不得显示可执行成功 |
| 库存与资源 | 确认不超预留；隔离/不足库存被拒绝；重复确认不重复扣减 |
| 旧版本/并发 | 改资源后旧计划确认被拒绝；两个请求争最后同一资源不能均确认 |
| 异常重排 | 两类边界事件各有前后差异、冻结事实和校验记录；原子替换受影响的未执行预留 |
| 模型理解 | 至少 10 条人工标注有限意图样例；核对实体、关键字段与来源；无依据内容不能越过确认 |
| 模型故障 | 无密钥/超时/错误抽取有清晰状态；结构化调度仍能操作；缺真实调用则模型项不通过 |
| 运行恢复 | 重启能读取已确认计划和事件；中断的计算标记失败或恢复，不能永久显示计算中 |
| 演示复现 | 独立操作者按说明启动；正常/故障/拒绝三条流程各连续重置演示 3 次成功 |

速度是待验收目标：固定 20 单场景的求解总预算先设 10 秒，超时报告真实状态；第 2 周记录本机初值，第 4 周用固定场景重复 20 次报告中位数、p95、成功率、硬件和原始时间。模型耗时、求解耗时、页面端到端耗时分别记录。20 次仅是 demo 小样本检查，不外推生产 SLA。

## 进度落后时怎么减范围
