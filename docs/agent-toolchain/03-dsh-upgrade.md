## A. 确定升级对象

1. 查找命令、快捷方式、用户启动脚本、npx/npm/pnpm 安装、桌面包装器和当前进程，定位用户实际使用的那一个 DSH 入口。只输出脱敏后的路径、版本、进程 ID 与绑定端口；不打印带 token 的完整命令行。
2. 核对 Node、包管理器、DSH_HOME、profile、存储类型、插件目录和迁移机制。不要把 `D:\Agent\DeepSeekHarness` 这个名称当作 DSH 源码 checkout；检查 package/git 事实。
3. 查官方源码、发布说明、npm 各包的 dist-tags、精确版本元数据和 peerDependencies。记录旧版本、候选目标、选择理由、breaking changes、Windows 支持与不可恢复迁移。用当前/目标的 help 或源码确认所有参数。

## B. 创建可恢复基线

4. 确认是否存在活跃任务或存储写入。采用官方一致性备份/在线快照方式；没有可靠在线方法时，在用户可接受的停止点再备份，不能边写边复制数据库并声称一致。先完成无需停机的检查；确需打断当前任务时，报告具体进程与未完成工作，再请求用户选择停止点。
5. 备份 settings、credentials、profiles 配置与锁文件、sessions、storages、attachments、presets 及必要移动访问设置。备份放在 `.dsh` 之外的用户私有目录，避免把备份目录递归复制进自身；缓存和 node_modules 可单列清单/可复现来源，不盲目重复复制。机密备份保持本机访问权限，不放进项目、共享盘、Git 或报告。
6. 记录备份清单、文件计数/校验、可恢复旧版本的包或来源，以及当前启动方式。对存储兼容性给出明确回滚条件。清空 npx 缓存不属于升级步骤。

## C. 隔离验证

7. 在独立 `DSH_HOME` 与临时工作目录安装精确目标版本。读取该版本官方说明确认 DSH_HOME 和端口覆盖方式，绑定本机不同端口。先测试空的新 home，再用一致性备份的数据副本验证迁移；始终不让试验实例连接原始会话/存储。新实例禁用可自动对外写入的定时任务、移动/远程入口或团队循环，避免双重执行。
8. 使用已有认证的受控副本完成必要探针，不输出秘密。验证官方核心启动、模型返回、读取/修改临时文件、工具调用、流式响应、取消/超时、创建/恢复会话、正常退出/重启、UI 静态资源与附件读取。
9. 先只加载目标所需官方组件，再按能力组恢复第三方插件：搜索/文档 → 浏览器/视觉 → 记忆 → 团队编排 → UI/额度 → 远程/移动。每组分别验收并记录组合冲突。涉及外部服务的插件用测试目标或只读探针，不能在副本环境触发真实消息、发布或业务写入。
10. 将每个插件标记为兼容、需指定升级、暂不兼容或未验证。确认插件市场是否会覆盖固定版本；稳定环境不能在启动时自动更新整套插件。可选不兼容插件可在新 profile 中暂时禁用并清楚报告；如果用户关键工具、历史数据或正常工作流程不能恢复，则保留旧入口，不声称完成升级。

## D. 切换与回滚

11. 核心、数据迁移及关键插件均通过后，安排停止旧实例并做最后一致性备份/增量处理，避免 canary 期间新增会话丢失。将原启动脚本/快捷方式切到已验证精确版本和正确 home/profile；不得只新建一个用户不会使用的全局命令后宣布完成。
12. 通过原日常入口重新启动，确认实际运行版本、旧会话数量与抽样恢复、附件、模型、MCP 和关键插件。只结束明确识别的 DSH/本次测试进程；不 kill 全部 Node。
13. 回滚时同时恢复旧程序入口、配置/锁和旧版本兼容的数据。若新版本已写入新会话，先保存这些增量并说明导回限制；禁止仅降级 binary 后让旧程序直接读取已迁移数据库，也不能无提示覆盖新数据。
14. 写脱敏报告与版本清单：before/after、实际入口、备份位置、目标来源、依赖矩阵、迁移与探针结果、停用插件、回滚办法。明确状态为 `UPGRADED_AND_VERIFIED`、`CANDIDATE_READY`、`ROLLED_BACK` 或 `BLOCKED`，不要混淆“已下载”“已验证副本”和“用户入口已升级”。

请持续完成所有可独立执行的准备与验证。若只能停在候选验证完成，明确尚缺的必要条件；不要为了展示最新版本而牺牲旧会话或关键插件。
