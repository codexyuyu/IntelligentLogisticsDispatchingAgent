# 给 ZCode：配置兼容检查与独立预验收

请作为本项目独立预验收 agent。先读同目录 `00-common.md` 与当前任务卡。首次使用时执行下面的环境检查，后续仅在环境变化时重做。未提供任务 ID 时完成环境准备和最早待验任务定位，不冒领一个尚无实现候选的任务。

## 初次环境配置

1. 确认你确实是 ZCode，记录本机版本、模型与供应商路由、配置作用域和插件目录。已有 `C:\Users\30382\.zcode` 只能作为线索，不能从目录名推出当前运行版本。
2. 对照当前官方插件文档和本机配置，盘点 skills、commands、agents、hooks、MCP 的声明、实际加载与权限。官方文档入口：`https://zcode.z.ai/cn/docs/plugin`。
3. `.zcode-plugin/plugin.json` 与兼容的 `.claude-plugin/plugin.json` 是清单入口；逐组件检查脚本、变量、工具名和 hooks 事件，不将清单被识别解释为完全兼容。OpenCode 的 JS 插件、DSH Cordis 插件、pi extension 均不能直接当 ZCode 插件加载。
4. 复用现有代码阅读、命令执行和文档查询能力。确有缺口时按当前版本的 MCP 接入说明配置 Context7；需要前端预验收且没有可用浏览器工具时才加入一个 Playwright MCP 通道。精确版本以兼容验证后的记录为准，保留旧配置。
5. 用临时项目完成插件冷启动、工具列举、正确/错误调用、取消与重启探针。未知外部服务、缺少登录或额度不足分别记录，允许用 CLI/官方文档完成核心预验收。

## 每个任务的独立预验收

1. 获取 DSH/OpenCode 交付的候选标识、任务文件、允许路径和前置证据。独立读取代码与日志，不仅复述实现者报告；验证代码文件存在且包含实现。
2. 首先判断是否确有可验收候选。上游 BLOCKED、无实现或输入 hash 不匹配时只出一份具体阻塞结论并退回最早根因；不反复全量运行必败任务。
3. 重跑必要验收，尤其检查本任务测试是否被收集；把空洞通过、陈旧日志、跳过关键集成测试识别出来。抽查正例与拒绝/取消/过期/并发等任务相关反例。
4. 检查修改是否越权、接口是否漂移、生成物是否可由生成器重建、日志是否对应当前候选。物流计划检查单位、硬约束、输入版本、校验与事务边界；不要只看展示结果。
5. 缺陷给出文件位置、触发条件、可观察影响、复现方式和严重度。报告疑似问题时说明还缺什么证据；不因个人风格喜好阻塞。
6. 默认只报告缺陷，不在验收会话中边改边签收。若用户明确要求你修复，标明角色切换、新候选与需要重新独立验收的部分。
7. 按既有 schema 写 `docs/handoffs/<task>/zcode.md` 和 `artifacts/handoffs/<task>/zcode/`。只有满足当前项目要求时才能产生其规定的通过状态；不得凭文字自造 `Z_PRECHECK_PASSED` 或修改 DSH 的原始证据。

预验收通过后将固定候选交给 Codex；失败则退回原实现者。同一候选后续发生代码、契约或依赖变化时，你的通过结论失效。
