# 给 Codex：插件维护与实际能力对照

请按本次用户指定模式维护 agent 工具链。先读同目录 `00-common.md`。默认模式为 `AUDIT`；只有用户指定 `UPDATE` 时才安装候选，指定 `BENCHMARK` 时才开展受预算约束的模型/agent 对照。本提示词执行一次，不自动创建周期任务。

## AUDIT：更新审计

1. 对当前运行清单中的宿主和插件查询官方最近 30/90 天的发布、breaking changes、弃用、对应兼容说明与可见 CI/维护状态；记录来源和 UTC 时间。重点看真正启用的插件，不扫描无关整个市场。
2. 区分“发布频繁”“维护响应”“兼容已证实”和“测试尚未做”。GitHub API 受限或来源不可达时标记未知，不能由 stars 推断稳定，也不把 API 失败说成项目停更。
3. 列出保留/候选升级/暂缓/淘汰候选及理由。无新增能力收益、修复收益或安全需要时允许保持旧的已验证版本。远程 MCP 不能本地固定服务端时，记录接口探针是否有变化。
4. 对浮动版本、重复浏览器/记忆/自治循环、旧失效工具定义和未使用插件给出具体去重建议。禁止直接删除正在被流程依赖的组件。

## UPDATE：逐个候选晋级

5. 在 stable 可恢复的前提下，在 candidate 每次只升级一个宿主或能力组；宿主有必要的配套依赖时一并作为一个变更单元。DSH 使用专门的 `03-dsh-upgrade.md`，不要用通用升级器覆盖它的存储/profile。
6. 更新正式通道候选；RC-only 项目如实标为预发布。快速扫描可以每天手动做，常规升级可每周集中验证；时间窗口只是建议，不能把“等了 72 小时”当通过标准。发布冻结期只接受必要修复。
7. 执行启动、核心工具、错误输入、取消/超时、会话恢复和回滚探针；补跑受影响项目的最小真实回归。通过后固定精确版本/commit与依赖锁，保留至少一个可恢复基线。
8. 输出 before/after、实际收益、证据、失败和恢复状态，不以安装命令 exit 0 宣告稳定。

## BENCHMARK：按项目任务测“实力”

9. 首先列出每个 agent 的实际模型和路由，检查是否多个前端实际调用同一模型。固定可比较的推理/时间/工具/成本预算；如果不能用相同模型，明确这是整套产品配置比较，不能归因于 harness 本身。
10. 从本项目选择小而代表性的离线任务集：一个领域边界缺陷、一个 API/契约任务、一个 PostgreSQL 并发任务、一个 React 错误状态/浏览器任务、一个 solver 反例与独立校验任务。选择有可评估基线、可隔离且不会改真实数据库的任务；解阻未完成时可用独立夹具，不把未通过主项目 Gate 作为选手缺陷。
11. 每个候选使用相同输入快照、验收要求、环境与预算，输出隔离；不泄露其他选手补丁或隐藏验收答案。记录首次通过、最终通过、有效测试、人工返工次数、完成时间、实际/估算费用、超时率与跨范围修改。
12. 免费额度不等于零延迟或零返工；费用不可见就标未知。WorkBuddy 只参加简单文档/页面任务，不强迫参加核心业务比拼。每工具一次结果只能作为初筛；在实际预算允许时复测关键候选，说明样本量和波动，避免伪精确综合分。
13. 由独立审查者依据业务不变量与隐藏验收判断结果。给出“哪类任务交给谁”的路由建议及失败条件，不只报一个总榜。不要因为偏爱某宿主调整验收标准。

输出：来源清单、更新候选表、可复现环境、探针/任务证据、结论与局限。只在本次预算内开展模型调用；缺少必要额度/授权时完成静态设计，明确 BENCHMARK 尚未执行。
