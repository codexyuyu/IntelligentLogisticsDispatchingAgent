# 文昌校区三车故障案例：回放一致性与界面清理

## 本轮交付

- 「异常处置」继续使用三车八单故障救援组件 `FaultRescueDemo`；「仿真回放」把同一组件以 `mode="replay"` 展示在首页主区域，地图与时间轴优先。两页读取同一个 `sessionStorage` 键 `fault_rescue_showcase_session_v2`，共享求解返回的 baseline / no_rescue / candidate 路线、故障时间、候选校验和本次会话的审批状态。
- 旧数据库联合运行仍在「历史联合运行与原有仿真回放」内，用户主动展开才挂载。**因此旧的一车 v0 不再冒充最新三车故障主案例**。
- 移除调度助手 `DecisionAnalysisPanel` 组件、样式及自然语言任务中的挂载位置，并移除业务问答的“AI 决策证据”展示卡片。保留原有 DeepSeek 工具解析、业务问答、工具执行审计与任务审批功能。
- 清理页面中的内部研发阶段编号、答辩准备口吻和元解释。对物流模拟路线、合成数据、人工审批/真实执行的差别仍保留简短标注。
- 修复配送站地图节点编号可能出现 `NaN` 的问题。

## AI 实际参与范围（务必如实回答）

- `POST /api/v1/integration/showcase/vehicle-breakdown/solve` **不调用 DeepSeek**：故障条件由固定示范场景构造，跨车接管方案由 OR-Tools `RoutingModel` 求解，代码独立校验约束，操作者决定是否在本地演示会话批准。
- 「调度助手」自然语言调度任务仍可使用 DeepSeek 工具解析；「业务问答」仍可通过工具查询并由模型解释。但是这些**不是故障救援按钮内部的求解步骤**，也不能说 DeepSeek 直接产生了候选路线。

## 本地验收（单次集中进行）

1. 安装项目的前端、后端依赖，启动服务，无须执行迁移。进入「异常处置」，运行“触发冷藏车 02 故障 · 运行 OR-Tools”，须看到 `status=solved` 且 `candidate_valid=true` 才能批准。若失败，按返回的诊断信息定位，不能将 `infeasible` 改成 `solved`。
2. 记录 O4/O5 实际接管车辆，批准候选；点击「仿真回放」。应默认显示相同 3 辆车、同样的 O3 故障交接点、299 秒故障时刻、6500 秒时轴，以及相同的已批准救援候选。分别观察故障前、故障后不救援、救援候选的路线变化。
3. 返回「调度助手」：不再有“AI Agent 决策分析”大卡片；自然语言任务、DeepSeek 解析来源、业务问答和原有任务审批仍正常。
4. 如需查看旧的一车联合运行，再打开「仿真回放」底部的历史回放折叠栏。确认新旧数据不会混显示。

无数据库读写、无 Git 推送。项目文案中保留“合成仿真 / 模拟路线”事实，不冒充实际 GPS、真实配送或真实业务审批。

## 静态检查

```
python scripts/check_replay_ui_consistency.py

```
