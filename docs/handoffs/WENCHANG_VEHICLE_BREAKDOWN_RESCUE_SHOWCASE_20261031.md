# 明日答辩：文昌校区「途中故障—跨车救援」交付说明

## 发生了什么变化

1. **异常处置**页面顶部新增 `FaultRescueDemo`，主案例为**三车、八单、车02完成O3后在安全节点故障**。现有一车两单的数据库延误历史仍在折叠的「高级功能」，不是本案例的求解来源。
2. 后端新增 `POST /api/v1/integration/showcase/vehicle-breakdown/solve`，要求现有 operator 角色，**不连接或修改 PostgreSQL**；用 `OR-Tools RoutingModel` 每次实时优化。
3. 故障车剩余 O4/O5 需要实际交接，OR-Tools 中给每张救援订单增加独立取货点，使用 `AddPickupAndDelivery`、同车约束、先取后送时间约束；备援车辆原本的剩余订单固定归属各自车、保留时间、沿途位置及在途服务。容量每车5件、时间维度6500秒，合成软时效罚金。
4. 同屏对照三方案：原计划、故障后不救援、跨车候选。重点展示恢复订单数、未交付数、迟到数以及可计算的示意成本。若候选不可行则禁止批准；不会伪造成本下降。
5. 人工批准只是当前浏览器 `sessionStorage` 中的**演示版审批**，不写数据库审批表、不改变真实派车或库存。地图回放使用该演示结果并保留原有文昌 2D 底图。
6. 移除异常处置页的 `DecisionAnalysisPanel` 大卡片；其他模块中的 DeepSeek 功能和审计未修改。

## 演示步骤（约90秒）

1. 进入「异常处置」，看到「车辆故障 → 其他车辆接管订单 → 智能重调度」。
2. 点击「触发冷藏车02故障 · 运行OR-Tools」。查看故障时间、O4/O5 接管、两种事故后方案。
3. 阅读 `OR-Tools` 计算出 O4/O5 由哪个车辆承接；确认救援车先到 O3 接货。
4. 点击「批准并回放接管路线」，从事故前一点开始播放；可选择「双方案同步回放」。
5. 如遇无解，界面明确显示原因，并禁止批准。不要展示“已优化”或虚假的里程收益。

## 数据口径 / 边界

- 地理锚点位于广西科技大学文昌校区周边，仓库、客户和路线均为**合成演示**，没有高德导航或 GPS 数据。为了保证故障时刻轨迹几何连续，该演示用直线段表示抽象道路矩阵；不应用于实际导航。
- 故障车完成 O3 后，在安全交接点停运；其他车辆保持各自已开始的服务与执行前缀。救援车辆必须先取 O4/O5 货品才能交付。
- `故障后不救援` 仍会有未交付订单，因此它的费用可能显得更低，不能把它解释为更优的业务方案。优先看**交付恢复率**；经济成本只包括合成里程费、迟到罚金。
- **本轮未建立数据库级跨车救援审批持久化**。以后若要正式投入业务运行，需要：完整货物交接/温控校验、可用载重与车辆资产、救援记录及事务式审批、统一运营路网成本。

## 现场验收建议

- 在授权的后端环境运行、并确认 OR-Tools 已安装。点击故障按钮必须返回 `status=solved`、`candidate_valid=true`，否则不应该批准。
- 核对 O4/O5 先 pickup 再 delivery，三车 ID 与地图一致，已完成订单不丢失。
- 切换「故障后不救援 / 接管候选」应看到订单覆盖变化；同一时间轴可暂停、拖动和双屏对比。
- 不要将本浏览器审批称作 PostgreSQL 业务审批。若老师询问说明是模型验证阶段演示，真实审批在原有业务流中已实现、跨车救援仍需集成。
