## 2. 接口/单位

任务包中声明的公开入口：

```text
GateEvidence(phase, revision, commands, exit_codes, artifact_hashes) -> GateDecision
```

落到已交付契约上的对应关系：

| 签名参数 | 契约字段 | 取值与约束 |
| --- | --- | --- |
| `phase` | `gate_id`（`GNN`）+ `docs/plan/PHASE_GATES.md` 的必需 Task 行 | `G00`–`G39` 共 40 个；编号缺失或重复即规划检查失败，`G00` 不能记录 |
| `revision` | `code_revision` + `dirty_tree_hash` | 有 Git 时用 HEAD(+dirty 树 hash)；本仓库无 Git 时用相关源文件清单 sha256 组合值，且必须可从仓库内容复算（`CONTRACT_FREEZE.json` 记为 `no-git`） |
| `commands` | `commands[]` | 每项 `{argv, cwd, exit_code, log_path, log_hash, test_counts}`；禁止 `shell=True` 拼接 |
| `exit_codes` | `commands[].exit_code` | 每条必须为 0；缺失或非零都不允许 `status=passed` |
| `artifact_hashes` | `input_artifact_hashes` + `acceptance_artifacts` | 判定所依赖的输入产物与附加断言产物的 hash；不一致即证据失效（F6） |
| （输出） | `GateDecision` ≈ 证据文件的 `status` + 执行器进程退出码 | `passed` 要求 F1–F9 全部成立；任一不成立写 `failed` 且进程非零退出 |

时间单位：`started_at`/`finished_at` 为 UTC ISO-8601。freshness 计算排除产物日志、时间戳与报告自身以避免自引用。本任务不定义求解业务单位；业务单位口径由 `P00-02` 冻结。

## 3. 输入输出样例

负例检查器的真实输出（`python tools/ai_coding_plan/check_gate_contract.py`，退出码 0，两条期望都被满足）：

```json
{
  "case_1_missing_dependency": {
    "expectation": "check fails",
    "errors": [
      "P01-01: missing dependency P99-01"
    ],
    "ok": true
  },
  "case_2_missing_exit_code": {
    "expectation": "evidence rejected",
    "errors": [
      "commands[0] has no exit_code; a Gate with unrecorded exit codes cannot pass"
    ],
    "ok": true
  }
}
```

样例 1 的输入构造（`check_gate_contract.py::missing_dependency_errors`）：先构造含 `P99-01` 的节点集合，再把 `P99-01` 从 `tasks` 中移除，于是 `P01-01` 的 `deps` 指向节点集合之外的 ID——这正是「依赖不可解析」的真实失败模式，交由冻结的 `validate_graph` 判定，得到 `P01-01: missing dependency P99-01`。

样例 2 的输入构造（`check_gate_contract.py::unsupported_evidence_errors`）：镜像 `artifacts/gates/G01.json` 的证据结构，但把 `commands[0]` 的 `exit_code` 剥离；检查器先校验 14 个必需证据字段，再逐条命令检查 `exit_code` 是否存在、是否为 0，得到 `commands[0] has no exit_code; a Gate with unrecorded exit codes cannot pass`。

Gate 证据中 `commands[]` 的目标形状（摘自 `GATE_EXECUTION_CONTRACT.md` 第 2 节字段表）：

```text
commands[]                每项 {argv, cwd, exit_code, log_path, log_hash, test_counts}
```

## 4. 状态与失败语义

- **默认失败关闭**：Gate 默认失败；只有 F1–F9 同时成立才允许写 `status=passed`。
- **缺退出码**：`commands[]` 中任一命令缺 `exit_code` 即证据无效（F3/F4），既不判通过，也不允许下游阶段启动。对应的可观察错误串为 `commands[0] has no exit_code; a Gate with unrecorded exit codes cannot pass`。
- **非零退出码**：该 Gate 写 `failed`，执行器进程以非零退出码结束，保证 CI 与人工调用都不会误判成功。
- **不可解析依赖**：任务的 `deps` 指向节点集合之外的 ID 时，DAG 校验失败，可观察错误串为 `P01-01: missing dependency P99-01`；Gate 不得通过。
- **零用例与 skip**：测试命令未真实收集到用例、或关键用例被 `skipped`，视为未验收（F5 判失败）；不得以零用例命令冒充通过。
- **hash 不一致与 fake**：产物 hash 与证据记录不一致时证据失效（F6）；用 fake/测试替身冒充真实引擎判失败（F8），fake 只允许出现在负例测试中。
- **失效传播**：影响某 Gate 的变更使其自身及全部下游 Gate 证据失效；禁止通过修改日期、重写状态字段或删除日志「恢复」证据。
- **契约解释边界**：正确的 Gate 授权流程是「前序 Gate 证据存在、未失效且 `status=passed`」才允许跨阶段（F2）；因此一条缺退出码的 `G00` 证据不构成可用的启动依据。本任务只定义该语义，不产生、也不修改任何 Gate 证据文件。
- **检查器自身的失败语义**：`check_gate_contract.py` 只有在两条期望都成立时返回 0；任一负例未复现（`ok=false`）即返回 1，属检查器失效而非 Gate 通过。

## 5. 实际限制

1. **本文档是规则契约，不是执行结果**：本轮没有运行任何应用测试、数据库、求解器、仿真或浏览器验收；`GATE_EXECUTION_CONTRACT.md` 第 7 节对此有明确声明。
2. **没有 Gate 证据文件**：`artifacts/gates/` 不存在（`artifacts/` 下仅有 `AI-CODING-PLAN.zip` 与其 `.sha256`）。因此本轮没有产出任何 `GNN.json`，也没有任何 Gate 被签收。
3. **Gate 执行器尚不存在**：`scripts/gates.py` 与 `scripts/check_architecture.py` 由 `P01-02` 交付；在它们交付并通过前，`G01` 及之后的 Gate 无法被判为 `passed`。
4. **无 Git**：`code_revision` 目前只能使用相关源文件清单 hash 方案（`CONTRACT_FREEZE.json` 记为 `no-git`）。
5. **检查器只覆盖两条负例**：`check_gate_contract.py` 演示的是「依赖不可解析」与「缺退出码」两条负例；F1、F2、F5–F9 的完整断言要等 `P01-02` 的实现与 `G01` 证据才能执行。
6. **规则通过不代表业务能力可用**：本任务的通过项全部是规划/契约静态检查。
7. **未决条目**：`docs/architecture/CONTRACT_FREEZE.md` 第 7 节记录的非阻断观察「`ARCH-0001` 追踪表 Gate 列与阶段屏障不严格对齐」把处置责任标给 `P00-03` 与契约变更任务；`docs/architecture/issues/` 目录是登记入口，当前没有立案的 issue 文件，本任务不修改冻结文档。
