# P01-02 · 分层检查、CI 与阶段证据执行器

计划版本 1.0.0(冻结清单)/1.1.0(任务书) · 阶段 Phase 01「Monorepo 与工程基础」 · 任务 ID `P01-02` · 负责方 A · 阶段 Gate G01

## 1. 已实现能力

本任务交付三件工程能力，全部为可执行工具，不含业务逻辑：

1. **分层架构检查** `scripts/check_architecture.py`：静态解析真实源码（AST + `tomllib`）后断言七层边界，退出码 0/1/2。检查项：
   - 每个模块必须归属已知层（`packages/<name>/src` 与 `apps/backend/src`）；
   - 层间导入方向：`domain` 零依赖；`contracts → domain`；`optimization → domain`；`simulation → domain`；`agents/evaluation → contracts`；`backend` 可装配全部；反向导入（如 `contracts → backend`）判失败；
   - 纯领域层不得导入任何第三方（`fastapi`/`pydantic`/`ortools`/`simpy`/`sqlalchemy`/`numpy`…），且其 `pyproject.toml` 必须声明零依赖；
   - 其他层只能导入自己成员 `pyproject.toml` 真正声明的发行物（`ARCH-UNDECLARED`）；
   - 禁止导入旧 `app.*` 命名空间与 `demo/`、`demos/` 教学探针（`ARCH-LEGACY`）；
   - 禁止在字符串字面量里引用另一成员的私有 `src` 路径（`ARCH-PRIVATE-SRC`）；语法错误必须报告而不是忽略（`ARCH-SYNTAX`）。
2. **阶段证据执行器** `scripts/gates.py`：`--phase NN --revision REV -> artifacts/gates/GNN.json`。它从**冻结的** `docs/plan/TASK_MANIFEST.json` 读取本阶段任务与命令并亲自执行，随后跑阶段附加验收断言、核验前序 Gate、DSH 证据、任务文档/ZCode 预验收/Codex review 记录与哈希新鲜度，全部通过才写 `status: passed`。提供 `--check-only`（只做新鲜度检查、不执行命令、不签收、不写文件）、`--skip-commands`（只验记录与断言框架，必定失败）、`--assertion <id>`（只跑指定断言）、`--root`（指向任意仓库根，便于隔离测试）。
3. **CI 与测试基础设施**：`.github/workflows/ci.yml`（双 OS 矩阵 + 前端 job + 凭据卫生 job）、`tests/conftest.py`（跨测试目录共用的隔离 fixture）、`apps/frontend/vitest.config.ts` + `apps/frontend/src/test/setup.ts`（jsdom 环境，禁止单测触网）。

G01 的五个附加验收断言（`PHASE_ASSERTIONS[1]`）全部为可执行检查，不是文档声明：

| 断言 id | 断言内容 | 实现方式 |
| --- | --- | --- |
| `clean-install-imports` | 六包在仓库外 cwd 也能导入，且解析到各自 workspace src | 生成临时探针脚本 → `uv run python` → 解析 `IMPORT_PROBE=` 输出 |
| `layer-boundaries` | 分层检查 exit 0 且 `violation_count == 0`、`modules_scanned > 0` | 真实执行 `check_architecture.py`（文本 + `--json` 两次） |
| `lock-reproducible` | `uv lock --check` exit 0；`uv.lock`/`package-lock.json` 存在且 npm `lockfileVersion == 3` | 真实执行 uv，读取 npm 锁 JSON |
| `runner-fails-closed` | 非零命令必被判失败 | 执行真实 exit=1 探针 + 注入失败计数复算判决 |
| `legacy-demo-untouched` | 旧 demo 未被覆盖 | 按 `BASELINE_INVENTORY.json` 逐文件重算 173 个 sha256，并比对 `demo.zip` 与 P01-01 证据记录 |

## 2. 接口/单位

任务书声明的唯一公开入口：

```text
python scripts/gates.py --phase NN --revision REV -> artifacts/gates/GNN.json
```

实际命令行契约：

| 参数 | 语义 | 退出码影响 |
| --- | --- | --- |
| `--phase NN` | 两位阶段号（`01`…`39`）；`00` 被拒绝并指向 `validate_plan.py --record-g00` | 用法错误 → 2 |
| `--revision REV` / `auto` | `auto` 时按内容清单计算 `content-sha256:<64hex>`（排除 `artifacts/gates`、`demo/`、`.venv`、`node_modules`、缓存目录） | — |
| `--check-only` | 只检查既有证据是否新鲜：命令日志 hash、输入产物 hash、revision、ZCode/Codex 记录；**不执行命令、不写文件** | 新鲜且已 `passed` → 0，否则 1 |
| `--skip-commands` | 不执行 manifest 命令与重断言（`runner-fails-closed` 仍执行真实探针）；结果必然 `failed` | 1 |
| `--out-dir PATH` | 把证据与日志写到别处（沙箱/自测运行）；该记录被标记 `official_gate_record: false`，**永不覆盖** `artifacts/gates/GNN.json` | 1 |
| `--assertion <id>` | 只运行命名断言（可重复） | — |
| `--root PATH` | 指定仓库根（默认脚本父目录） | — |

单位与版本口径：证据 `schema_version = "1.0.0"`；命令耗时用整数毫秒；`started_at`/`finished_at` 为 UTC ISO-8601；时间/长度/重量等业务单位本任务不涉及（不产生业务数据）。

分层检查的退出码：`0` 全部通过；`1` 有违规；`2` 配置错误（仓库根不存在）。

## 4. 状态与失败语义

| 情形 | 判定 | 证据/日志行为 | 进程退出码 |
| --- | --- | --- | --- |
| manifest 命令 exit≠0 | 该 check `failed` | 保留完整 stdout/stderr，日志 hash 入证据；**不删旧记录** | 1 |
| pytest 零用例（如 `exit_code=4`） | `failed`（"zero-case run is not acceptance evidence"） | 同上 | 1 |
| pytest 有 `failed`/`errors`/`skipped` | `failed` | 计数写入 `test_counts` | 1 |
| 日志为空 | `failed` | 空日志即证据无效 | 1 |
| 分层检查有违规 | `layer-boundaries` `failed` | 记录违规数 | 1 |
| 前序 Gate 记录缺失、仅写 `status`、字段不全、命令/日志/输入/依赖哈希不合规或存在依赖环 | `previous-gate:GNN` `failed`（逐条列出违反项） | 读取真实记录并重算哈希；`log_sha256`（本执行器）与 `log_hash`（规划检查器）按具体 schema 兼容，缺两者即拒 | 1 |
| DSH 证据缺失或状态非 `READY_FOR_ZCODE`/`Z_PRECHECK_PASSED` | `dsh-evidence:<TASK>` `failed` | 记录实际 status | 1 |
| 任务文档/完成报告缺失 | `docs:<path>` `failed` | 逐路径报告 | 1 |
| ZCode 预验收记录缺失、`task_id`/`phase_gate` 不符、`verified_input_hashes` 缺失/为空/格式非法/未覆盖必需输入 | `zcode-precheck:<TASK>` `failed` | 逐条列出（含未覆盖的必需输入清单） | 1 |
| ZCode 记录 `verified_input_hashes` 漂移 | `failed`（"stale input hash"） | 列出漂移路径 | 1 |
| Codex review 缺失 | `codex-review` `failed` | 提示不可签收 | 1 |
| Codex review 覆盖的 revision 与当前不一致 | `failed` | 同时给出两个 revision | 1 |
| Codex review 输入哈希漂移、为空或缺失 | `failed` | 列出漂移路径或说明空集合不是证据 | 1 |
| 全部通过 | `passed`，写入 `artifacts/gates/GNN.json` | 旧记录压入 `runs[]`（最多 20 条）保留审计 | 0 |
| `--check-only` 全部新鲜 | **不写 passed**，只输出检查结果 | 不产生任何文件 | 0 |
| `--check-only` 发现漂移 | 输出 `STALE …` | 不产生任何文件 | 1 |
| `--phase 00` / 非数字 | 用法错误 | 提示 G00 由 `validate_plan.py --record-g00` 记录 | 2 |

错误码约定（`INVALID_INPUT` 等 HTTP 语义）属业务边界，本任务不产生业务错误路径；本工具用"退出码 + check id + 结构化 detail"表达失败，绝不把失败包装成成功。

## 5. 实际限制

- **G01 仍未签收**：`artifacts/gates/G01.json` 是 `failed`，因为（a）`P01-03` 尚未交付（其命令与文档缺失）；（b）ZCode 预验收记录与 Codex review 记录按设计不属于 DSH 白名单，必须由对应审查角色写入。DSH 自测通过 ≠ Gate 通过。
- **`docs/workflow/HANDOFF_CONTRACT.md` 不存在**：审查记录的存放格式由本任务自行固定为 `artifacts/handoffs/<TASK>/zcode/precheck.json`（`status: Z_PRECHECK_PASSED` + `verified_input_hashes`）与 `artifacts/gates/GNN-codex-review.json`（`gate_id`/`status`/`reviewer`/`code_revision`/`verified_input_hashes`）。契约文档就位后应改为引用它并登记差异。
- **`--skip-commands`** 是显式逃生舱：它让记录/断言框架可在自身测试中被验证，但结果必然 `failed`，每个被跳过的断言都在 `detail` 里写明 `--skip-commands was requested`，不可能被误读为通过。
- **`--out-dir` 与官方记录隔离（本任务修复的真实缺陷）**：测试套件内的真实仓库运行一度直接写 `artifacts/gates/G01.json`，把已交付的验收记录覆盖成 `--skip-commands` 的失败记录，使被审计的 Gate 状态取决于测试执行顺序。现规定：只有不带 `--out-dir` 的运行才代表阶段 Gate 记录（`records_official_gate=True`）；带 `--out-dir` 的记录会写入 `official_gate_record: false` 与说明，且集成测试在运行前后断言官方记录字节不变。
- **`runner-fails-closed` 探针**固定返回 exit=1 并被判失败；它证明的是执行器的失败关闭逻辑，不是业务失败。
- **层检查的第三方清单是白名单**：未列入 `THIRD_PARTY` 的新依赖其导入不会被判违规，只会在"声明一致性"上被忽略；新增依赖时必须同步该表（后续任务需注意）。
- CI 仅在本机以静态文本校验方式检查（无 GitHub 运行记录）；`npm --workspace @logistics/frontend run test` 在 P24-01 前后端没有测试文件时由 `--if-present` 兜底，**不算验收证据**。
- 本任务不改动任何业务契约、不新增领域类型、不触碰 `demo/`。

## 7. 返工 2026-10-01（G01 前置修复，`P01-02 / rework-2026-10-01`）

本轮只修 `scripts/gates.py` 的判定与测试结构，不新增 manifest 节点、不签收任何 Gate、不改业务契约或依赖。三项规则的**唯一权威实现**就是这两个常量块与相应函数，本文是它们的说明。

### 7.1 候选 revision：确定性相关文件清单（缺陷 2）

`compute_revision()` 不再是整树扫描。相关输入集合由白名单推导（`REVISION_INCLUDE_ROOTS`、`REVISION_INCLUDE_FILES`、`REVISION_INCLUDE_CONTRACT_ROOTS`、`REVISION_INCLUDE_PLAN_FILES`）：

- 实现与测试源码：`apps/`、`packages/`、`scripts/`、`tests/`、`tools/`、`contracts/`、`data/`、`deploy/`、`.github/`；
- 根构建/配置/锁：`pyproject.toml`、`uv.lock`、`package.json`、`package-lock.json`、`.python-version`、`.node-version`、`OWNERSHIP.json`；
- 冻结公共契约：`PROJECT_MASTER_PLAN.md`、`TASK_GRAPH.md`、`docs/architecture/**`、`docs/api/**`、`docs/algorithms/**`（业务 Schema 与生成器属于相关输入，未排除）；
- 执行器直接消费的规划输入：`docs/plan/{TASK_MANIFEST.json,PHASE_GATES.md,GATE_EXECUTION_CONTRACT.md,TEST_FIXTURES.md}`。

排除：`artifacts/**`、`tmp/**`、`.mimosa/**`、`tools/bin/**`（vendored 二进制）、`demo/**`、`demos/**`、`platform/**`、`backend/**`、`frontend/**`、`benchmarks/**`、`node_modules`、`.venv`、各缓存目录、`.pyc/.log/.zip/.png/.jpg/.pdf`，以及流程文档与全部产出记录（`AGENTS.md`、`README.md`、`AI-CODING-PLAN.md`、`docs/prompts/**`、`docs/agent-toolchain/**`、`docs/workflow/**`、`docs/implementation/**`、`docs/handoffs/**`、`docs/reviews/**`、`docs/plan/{USER_REQUIREMENTS,REQUIREMENTS_TRACEABILITY,PACKAGE_MANIFEST,VERIFICATION_REPORT}.*`）。

排序与复算方式（可手工复算，测试中独立重算过同一公式）：

```text
路径按仓库相对 POSIX 路径字节序排序；不存在的根或文件直接缺席（不报错）
code_revision   = "content-sha256:" + sha256("\n".join(f"{path}\0{sha256(content)}"))
dirty_tree_hash = "content-sha256:" + sha256("\n".join(f"{path}\0{size}\0{sha256(content)}"))
```

`code_revision` 是实现候选标识，`dirty_tree_hash` 是同一相关文件集的工作树指纹；两者用不同公式分别记录，均不含日志/报告/审查记录，因此**写入证据不会自扰动**，而改动相关代码/配置/契约/测试一定改变两者。

### 7.2 审查记录输入哈希：必须非空、可核验、覆盖必需输入（缺陷 3）

`recorded_input_problems()` 对 ZCode 预验收与 Codex review 使用同一套规则：`verified_input_hashes` 必须是对象且非空；每个键是仓库内相对路径、值是 64 位小写 sha256、文件存在且哈希一致；ZCode 记录还须覆盖 `required_precheck_inputs()`（`docs/plan/TASK_MANIFEST.json`、`docs/plan/PHASE_GATES.md`、任务 prompt、本任务 DSH 证据），并且 `task_id`、`phase_gate`、`reviewer`、`status` 必须匹配。空集合、缺失集合、错误哈希、关键输入遗漏、错误 `task_id`/`phase_gate` 一律拒绝。

### 7.3 前序 Gate 证据：按 F2/F3/F4/F6 完整校验（缺陷 4）

`check_previous_gates()` 不再只看 `status`。对每个前序 Gate 记录校验：schema 必需字段（按 `planner`/`runner` 两种真实生产者 schema 分别要求，见 `gate_record_schema()`）、`gate_id` 匹配、`status=passed`、`code_revision`/`reviewer`/时间戳类型；每条命令的 `argv`/`cwd`/`exit_code`（`type(...) is int`，`True`/`False`/`0.0`/`"0"` 均拒绝）及原始日志的存在、非空与哈希；`input_artifact_hashes` 非空且逐项与磁盘一致；`dependency_evidence_hashes` 只允许指向更早的 Gate、哈希与磁盘一致，并拒绝自引用、前向引用与依赖环。

兼容性按具体 schema 明确处理：规划检查器写 `log_hash`，本执行器写 `log_sha256`，两者都接受；**两者都没有则拒绝**（不以忽略日志校验换取兼容）。规划 schema 从未写 `started_at`/`dirty_tree_hash`/`acceptance_artifacts`，因此这三项只在 runner schema 下要求，此项差异在 `PLANNER_SCHEMA_FIELDS`/`RUNNER_SCHEMA_FIELDS` 中显式登记，其余元素对两种 schema 一视同仁。
